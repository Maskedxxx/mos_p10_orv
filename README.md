# Платформа ОРВ · модуль П-10

Сервис разбирает нормативный правовой акт города Москвы и возвращает
готовый Excel: **карту гипотез** — что в акте не так и чем это измерить,
и **запрос показателей** — что спросить у органа-разработчика.

Это работа, которую аналитик оценки регулирующего воздействия делает
вручную несколько дней. Сервис делает её примерно за 10 минут, а человек
проверяет результат.

Заказчик — АНО «Мосстратегия» / Департамент экономической политики
и развития города Москвы.

---

## Что на входе и что на выходе

**Вход** — файл акта: `.docx`, `.pdf` или `.doc`. Формат неважен,
сервис определяет его сам. При загрузке отмечается тип акта (можно
несколько; без типа разбор не запустится) — от него зависят обязательные
показатели бланка. В «Настройках прогона» — потолки заходов поиска
в интернете для индикаторов 3, 4, 10, 11 (от 1 до 50); выбор хранится
в прогоне и действует и в диалоге по нему.

**Выход** — один файл `.xlsx` с шестью листами:

| Лист | Что на нём |
|---|---|
| Как заполнять | инструкция эксперту: акт, тип акта и дата разбора — от сервиса, ФИО и дата отзыва — оранжевые клетки, семь правил |
| Карта гипотез | индикаторы с претензией: что не так, к чему приводит, чем измеряется и какая динамика подтвердит гипотезу, какие нужны данные, на чём основан вывод |
| Запрос показателей | пустой бланк для органа-разработчика: сначала обязательные показатели по типу акта, затем — из гипотез; что посчитать, за какие годы, ради какой гипотезы |
| Вопросы органу | вопросы словами — то, что нельзя запросить числом или перечнем; у каждого пункт акта и строка карты; вопросов нет — так и написано |
| Вердикты | все 12 индикаторов: вердикт, обоснование, цитата и «Где подробнее» — строка карты или лист ошибок; «нет данных» подсвечены |
| Ошибки прогона | что не отработало, и «нарушен», по которому не построена гипотеза; пусто — значит разбор прошёл целиком |

У каждого листа сверху одна строка-подпись: что на нём лежит и по какому
принципу отобрано. Карта и два бланка проверяют весь акт, «Вердикты»
и «Ошибки прогона» показывают, что ни один из двенадцати индикаторов
не потерялся по дороге.

На листах карты, запроса, вопросов и вердиктов справа — оранжевые колонки
для оценки экспертами («Оценка (1–5)», «Замечание»; на вердиктах —
«Согласны?», «Если нет — какой верный», «Замечание» и с 2.7 «Где искать»: где
лежат сведения для «нет данных»). Они есть всегда, с выпадающими списками (1…5, да/нет):
эксперты заказчика дорисовывали их руками при тестировании, теперь файл
сразу готов к разбору (пул 3, 2026-09-04).

**Листы связаны в обе стороны.** В карте у каждой гипотезы стоят номера
строк запроса, которыми она закрывается. В запросе у каждого показателя —
номера строк карты и индикаторы, ради которых его спрашивают. Получив от
органа цифры, аналитик сразу видит, к какой гипотезе они относятся, а не
перебирает карту вручную.

**Данные каждой гипотезы разделены на группы.** Сверху то, что
запрашивают у органа: числа — в бланк запроса, вопросы словами — на лист
«Вопросы органу». Ниже открытые источники с адресом, откуда их взять
(torgi.gov.ru, прайсы, реестры). В бланки уходит только то, что для органа:
лист отправляют наружу, и всё напечатанное в нём орган читает как задание
себе. Цифра, которую, по словам эксперта, не ведёт никто, помечается
«нигде не ведётся» (операция диалога) и уходит из бланка.

**Колонка «На чём основано» — доказательная база вывода.** Дословная
цитата из акта с номером пункта, а под ней адреса внешних источников,
если индикатор ходил в Гарант или интернет. Цитаты может не быть — тогда клетка
прямо говорит почему, а не остаётся пустой.

## Природа задачи

Есть методика АНО «Мосстратегия»: **двенадцать индикаторов эффективного
регулирования**. Это двенадцать вопросов, которые задают любому акту —
не требуют ли лишних бумаг, можно ли подать документы электронно, не
ссылается ли акт на отменённые нормы, и так далее.

Аналитик читает акт и отвечает на каждый вопрос. Там, где ответ «нарушено»,
он формулирует гипотезу: к чему это приводит, кого задевает, каким
показателем это измерить и где взять цифры. Часть цифр есть в открытых
источниках, часть надо запрашивать у органа — из них и складывается запрос.

Сервис повторяет эту работу.

**Ключевое решение — декомпозиция.** Акт не отдаётся одной модели с просьбой
«найди всё, что не так»: такой ответ приходит быстро, но получается
поверхностным, без опоры на текст. Вместо этого каждый индикатор проверяет
отдельный вызов модели со своей инструкцией, и каждый обязан подкрепить
вывод **дословной цитатой с номером пункта**. Без цитаты вердикт не
принимается — эксперту нечего было бы проверять.

опираются все следующие вызовы.

### Что делает каждый узел

**1. Конвертация.** Файл превращается в размеченный текст. Нумерация
пунктов, заголовки и таблицы сохраняются — без номеров пунктов дальше
нечем будет сослаться на конкретное место акта. Работает `docling`, он
сам определяет формат по содержимому. Устаревший `.doc` сначала
перегоняется в `.docx` через LibreOffice.

**2. Паспорт акта.** Один вызов модели по строгой схеме (`ActPassport`):
правила — в описаниях полей контракта, промпт только велит заполнить схему
по ним. Ответ модели проверяет `ActPassportOutput` — тот же паспорт плюс
правила, добавленные после прежних прогонов; сохранённые паспорта читаются
как `ActPassport`, поэтому старые прогоны открываются как раньше. Паспорт
отвечает на вопрос «где искать», а не «что написано»: реквизиты
с органом-разработчиком (`Requisites.developers` — кто ведёт
применение акта: у него данные о заявках, отказах, проверках); статус
(проект или принят, дата вступления в силу, отложенные пункты); кому обращён
акт; что он делает как документ; и семь объектов — обязательные требования,
процедура с участием внешнего лица, документы, сроки, ссылки на акты
и органы, распределение и допуск, контроль. У каждого объекта три
состояния: **есть** (с пунктами), **нет** (с обоснованием, где искали)
и **не понял**. Если по тексту не ясно, кто ведёт акт, агент паспорта ищет
разработчика в Гаранте (`garant_search`); без токена Гаранта — только
по тексту. Паспорт подаётся агентам индикаторов, гипотез и запроса вторым
блоком после полного текста акта — как подсказка: всё проверяется по тексту,
пруф только из текста. Из паспорта же — годы бланка, его адресат и шапка
Excel. Провал паспорта останавливает прогон. Заменил саммари (версия 2.3).

**3. Вердикты.** Двенадцать вызовов модели одновременно, у каждого свой
контракт ответа (`Indicator01Output` … `Indicator12Output`): сначала таблица
проверки — например, каждый документ, который подаёт заявитель, или каждая
ссылка акта, — потом разбор, потом вердикт. Что считать нарушением, а что
нарушением *не* является, записано в описаниях полей контракта; промпт
только направляет. Что вердикт следует из таблицы, проверяет код: не следует —
ответ отвергается, и модель переспрашивают с текстом ошибки (до трёх
попыток). «Не применимо» тоже следует из таблицы: проверять в акте нечего
(у индикатора 10 — акт не вступил в силу или обращён только к органу).
Таблица сохраняется рядом с вердиктом — `03_verdicts/NN.checks.json`.
Инструменты есть только у индикаторов 3, 4, 10, 11 — Гарант и интернет;
остальные восемь работают только по тексту акта. Проверки не видят друг
друга — это защищает от того, чтобы одна догадка потянула за собой остальные.

**4. Разбор корзины.** Чистый код, раскладывает двенадцать вердиктов
по четырём кучам. Ничего не выбрасывается: все двенадцать доходят до
итогового файла, просто на разные листы.

**5а и 5б. Гипотезы.** Две ветки идут одновременно. Из нарушений пишутся
гипотезы: одна проблема — одна гипотеза, у неё может быть несколько
эффектов (для бизнеса и для города от одного механизма), у каждой —
основание дословно из карточки вердикта и род нарушения: издержки либо
дефект нормы. Из пробелов в данных пишутся вопросы к практике применения,
строго в рамках того, что нашёл агент индикатора; «нет данных» по
индикаторам 1–6 гипотез не порождает — это незавершённая проверка
по правовой базе, она идёт в карту строкой «Нужна ручная проверка».
Цитату гипотезы код мягко сверяет с текстом акта: пересказ не проходит.
Вопросы органу словами модель пишет отдельным списком. Числа для органа,
которые индикатор 10 записал при «нет данных», доходят до гипотез: потерянные
агентом код дописывает сам.

**6. Сборка карты.** Проверки работали порознь, поэтому разные индикаторы
могли зацепить одну проблему с разных сторон. Здесь модель впервые видит
все гипотезы разом и сливает повторы, сохраняя все индикаторы, эффекты,
основания и данные. Код заранее находит пары гипотез с общим пунктом акта
и подаёт их как кандидатов — по каждому модель обязана дать решение
«слить / не слить» с причиной; пропуск фиксируется в логе.

**7. Запрос показателей.** Из карты отбирается то, чего нет в открытом
доступе, и склеивается по смыслу: если три гипотезы просят «количество
заявок» разными словами, чиновник должен увидеть один вопрос. Одна
позиция — одна величина с единицей измерения из закрытого перечня (доли
и проценты обычно не запрашиваются: их считает аналитик; исключение —
официальный показатель органа, когда открытые источники расходятся).
Перечни и реестры идут отдельным блоком без колонок годов, вопросы
словами — на своём листе. Каждая позиция помнит, из каких показателей
карты собрана, — код проверяет, что ни один не потерян. Колонки годов —
три последних завершённых года, но не раньше года вступления акта в силу.
В бланке первыми — обязательные показатели по типу акта, формулировками
формы эксперта «Форма для ИИ 2.0» (`app/mandatory_indicators.py`); пропущенный
моделью показатель код дописывает дословно.

**8. Excel.** Шесть листов плюс обратные ссылки между картой и бланками;
в версиях диалога — ещё лист «Журнал изменений».

## Двенадцать индикаторов

Список закреплён методикой и одинаков для всех актов. Восемь вопросов
решаются только по тексту акта, четыре — ещё и по правовой базе Гарант
и интернету.

| № | Что проверяется | Где ищется ответ |
|---|---|---|
| 1 | Орган сам запрашивает документы, которые у государства уже есть | текст |
| 2 | Документы можно подать электронно | текст |
| 3 | Акт не ссылается на отменённые нормы и упразднённые органы | текст + Гарант (статус ссылок) + интернет |
| 4 | Требование не повторяется и не расходится в самом акте и в актах, на которые он ссылается | текст + Гарант + интернет |
| 5 | Ошибку в пакете можно исправить, а не подавать всё заново | текст |
| 6 | У обязательного требования есть срок действия | текст |
| 7 | Одно и то же действие не совершается дважды — ни лицом, ни органами | текст |
| 8 | Заявитель может подготовить документы сам, и лишних среди них нет | текст |
| 9 | Из текста понятно, что требуется и что будет за невыполнение | текст |
| 10 | Норма реально работает, а не существует на бумаге | текст + Гарант (доклады органа, суды) + интернет |
| 11 | Сроки не затянуты: сравнение с федеральной нормой и с другими сроками акта | текст + Гарант (федеральный акт) + интернет |
| 12 | Требования не отсекают часть участников без оснований | текст |

Гарант подключён как MCP-сервер `mcp.garant.ru` (файл `deploy/garant_mcp.json`
без токена; токен — в файле машины `~/.config/garant/token`, в репозиторий
и трейсы не попадает). Каждому индикатору разрешены только свои инструменты
Гаранта (`INDICATOR_GARANT_TOOLS`), остальные от модели скрыты; Гарант идёт
мимо прокси машины. Сравнение с другими регионами в 2.7 снято: поля «Регионы
сравнения» на странице больше нет.

## Четыре вердикта и что из них следует

Это главная развилка пайплайна. От вердикта зависит, куда пойдёт индикатор.

| Вердикт | Что означает | Куда идёт |
|---|---|---|
| **нарушен** | проблема найдена в тексте, есть цитата и пункт | → гипотеза → карта |
| **нет данных** | тема есть, но проверить нечем | → гипотеза-подозрение → карта → **запрос органу** |
| **соблюдён** | требование выполнено, тоже с цитатой | → лист «Вердикты» |
| **не применимо** | темы в акте нет и быть не должно | → лист «Вердикты» |
| **ошибка** | проверка сорвалась, попытки исчерпаны | → лист «Ошибки прогона» + строка на листе «Вердикты» |

Три правила, которые заложены намеренно:

**«Нет данных» никогда не превращается в «нарушен».** Обвинить акт там,
где его просто не проверили, — худшая из возможных ошибок: разбираться
с несуществующей проблемой будут живые люди.

**Сорвавшаяся проверка никогда не превращается в «соблюдён».** Молча
проглоченный сбой дал бы акту зелёный свет там, где его не проверяли.
Поэтому есть отдельный статус «ошибка» и отдельный лист под него.

**Гипотеза не попадает в карту, если для неё нельзя назвать показатель
эффекта и источник данных.** Это тормоз против разрастания: у коллег из
ВШЭ без такого ограничения вышло 39 карточек вместо десяти.

## Выжимка для эксперта

С версии 2.5. Каждый агент пишет полный разбор — он нужен ему для рассуждения,
а нам для анализа — и рядом выжимку для эксперта: пункты с фактами (пункт акта,
кого касается, число, срок). В Excel идёт только выжимка: «Обоснование» вердикта,
«Гипотеза», «Как считать», «Что подтвердит гипотезу», «Основание из вердикта».
Полный текст — в JSON прогона (`03_verdicts/NN.json`, `06_map.json`: поля без
окончания `_brief`); его же видит помощник диалога. Прогоны до 2.5 выжимки не имеют —
Excel показывает полный текст.

## Диалог с результатом

С версии 2.5 (ветка `dialog-v1`). Под карточкой готового прогона — панель
«Работа с результатом». Аналитик, он же эксперт, спрашивает, почему такой
вердикт, правит формулировки, передаёт решения эксперта, просит перепроверить
индикатор или досчитать гипотезы — не прогоняя акт заново.

```
сообщение ──▶ помощник (07_dialog.md) ──▶ ответ + план из операций
                                              │ «Применить»
                                              ▼
            шаг без агента ──▶ сразу новая версия: Excel, журнал, пометки
            шаг с агентом  ──▶ «было — стало» ──▶ «Принять» ──▶ новая версия
```

| Без агента — сразу новая версия | С агентом — сначала «было — стало» |
|---|---|
| правка текста · смена вердикта · удалить, добавить, слить строки карты · пометить цифру: нигде не ведётся · удалить, разделить позицию запроса | перепроверить индикатор · построить гипотезы по индикатору · дополнить запрос под новые строки карты |

- **Помощник сам ничего не пишет.** Он отвечает и предлагает план из закрытого
  списка; выполняет код после подтверждения.
- **Помощник помнит разговор (2.7).** Одна сессия CLI на прогон
  (`dialog/session.json`): следующий ход продолжает её со строкой «какая версия
  сейчас и что изменилось с прошлого хода». В системном промпте — карта прогона
  (`app/run_map.py`: какие файлы есть, все поля их контрактов, какая колонка
  Excel из какого поля), акт и паспорт. Вердикты, таблицы проверки, карту, бланк
  он читает сам — инструментами `list_artifacts` и `read_artifact` своего
  MCP-сервера `app/mcp_run.py` (только файлы этого прогона); ещё у него весь
  Гарант и интернет. Нет файла токена Гаранта — ход идёт без Гаранта, а не
  падает.
- **Выгрузки Гаранта** (30 в месяц на весь токен, общие для всех) помощник делает
  сам; после хода с выгрузкой сервис пишет в чат «потрачено N, осталось M». На
  панели — шаги помощника по ходу его работы (и свёрнуто под ответом), источники
  ответа и строка остатка лимитов Гаранта.
- **Слово эксперта исполняется без спора.** Перепроверку помощник предлагает
  только по просьбе и не подсказывает агенту, какой вывод нужен.
- **Каскад простейший.** Считается только запрошенное; затронутое помечается
  «устарело» в чате и в Excel, досчёт — отдельным шагом.
- **Версии.** v0 — исходный разбор, не меняется. Каждое изменение — новая
  версия со своим Excel, строкой листа «Журнал изменений» и пометками строк;
  «Вернуть» делает новую версию, ничего не стирая.
- **Файл эксперта.** Заполненный Excel разбирается в очередь замечаний,
  по одному в диалог.
- **Состояние видно всегда.** Строка над чатом: «Готово», «Помощник думает…»,
  «Выполняю шаг k из n», «Ждёт вашего решения», сбой, «Только просмотр».
  Действия идут на сервере, поэтому перезагрузка и второе окно видят то же;
  правит одно окно.
- **Только прогоны 2.4 и новее** — карты старых версий не проходят контракт.
- **Сессии.** Логин один на всех, люди различаются по сессии браузера (метка
  `s-7f3a91`). Каждое действие на странице — строка `var/logs/actions.jsonl`
  (время, сессия, адрес, действие, прогон); в чате метка стоит у реплик и решений.
- **Конец работы с актом (2.7).** Сессия работы с актом — вся папка прогона: разбор,
  Excel, чат. Она закрывается кнопкой «Завершить работу» или сама, если 60 минут
  нет событий в её журнале (`events.jsonl`); с идущим разбором или действием
  в чате — не закрывается. Закрытие — насовсем: чат и правки недоступны, Excel
  можно скачать; итог — `session_summary.json` (`app/sessions.py`).

```
  json_fix.py       починка битого JSON ответа модели по схеме контракта
  mandatory_indicators.py  обязательные показатели бланка по типу акта
  nodes/            восемь узлов пайплайна, по файлу на узел
  pipeline.py       оркестратор: порядок, барьеры, прогресс
  dialog.py         диалог: ход помощника, сессия CLI, чат, состояние, очередь замечаний
  run_map.py        карта прогона для помощника: файлы, поля контрактов, колонки Excel
  mcp_run.py        MCP-сервер помощника: чтение файлов своего прогона
  garant_limits.py  остаток месячных лимитов Гаранта
  operations.py     одиннадцать операций диалога поверх узлов, откат версии
  versions.py       версии прогона: снимки, журнал, восстановление после сбоя
  feedback.py       разбор заполненного экспертом Excel
  actions.py        журнал действий на странице: сессия браузера, адрес, действие
  sessions.py       конец сессии: кнопка или час без событий, итог session_summary.json
  web.py            веб-страница на NiceGUI, вход по паролю, очередь, панель диалога
prompts/            18 промптов, по файлу на вызов модели: паспорт, 12 индикаторов, 04a, 04b, 05, 06, 07 (диалог)
scripts/            watch.py — живая лента прогона, session_report.py — разбор сессии
tests/              больше 900 тестов
deploy/             юниты systemd и сторож, garant_mcp.json — подключение Гаранта (без токена)
```

**Промпты лежат файлами, а не в коде.** Их правят люди, не разбирающиеся
в Python, и правят часто — это бизнес-логика, а не программирование.

**Контракты обязательны на каждой границе.** Узел принимает и возвращает
pydantic-модель, а не словарь. Все поля моделей — латиницей: `claude -p`
отвергает кириллические имена полей в JSON-схеме.

**Агент получает только своё.** Каждый вызов `claude -p` изолирован
от машины (без её CLAUDE.md, навыков, плагинов и чужих MCP-серверов)
и запускается со своим коротким системным промптом
(`SERVICE_SYSTEM_PROMPT`, флаг `--system-prompt-file` или `--system-prompt`)
вместо стандартного промпта Claude Code. Инструменты — ровно те, что
разрешены узлу; неразрешённые инструменты Гаранта скрыты от модели
(`--disallowedTools`).

Вне прогонов (2.5): `var/logs/actions.jsonl` — журнал действий на странице,
`var/logs/service.log` — лог сервиса с ротацией; с 2.7 ещё `var/logs/service.jsonl` —
журнал сервиса: старт, очередь прогонов, закрытие сессий.

Корень папки — текущая версия: весь код, кроме диалога, читает артефакты
оттуда и о версиях не знает.

**Сырые ответы модели сохраняются всегда**, включая попытки, которые
не прошли проверку. Без них нечем разбираться, почему модель ответила
не так.

## Как запустить

Нужен Python 3.12 и установленный `claude` CLI с доступом к API.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# доступ к веб-странице
cat > .env.secrets <<EOF
P10_AUTH_USER=admin
P10_AUTH_PASSWORD=<пароль>
P10_STORAGE_SECRET=<случайная строка>
EOF
chmod 600 .env.secrets

.venv/bin/python -m app.web        # страница на порту 8030
```

Без заполненного `.env.secrets` сервис не стартует — это сделано намеренно,
чтобы страница не поднялась нараспашку.

Гарант: токен одной строкой в файле `~/.config/garant/token`. Без него паспорт
и помощник работают без Гаранта, а индикаторы 3, 4, 10, 11 получают вердикт
«ошибка» с причиной — тихо проверять без правовой базы они не будут.

Фирменный стиль «Экономика Москвы» (27.10, `app/brand.py`): файлы — в `var/brand/`, вне git (репозиторий публичный,
шрифт — по лицензии заказчика): `fonts/TTMoscowEconomy-{Regular,Medium,Bold}.woff2`, `header.svg` (эмблемы в шапке),
`login_band.svg` (полоса узора на входе), `favicon.svg` (значок вкладки). Сервис смотрит папку один раз при запуске;
без неё — фирменные цвета, но стандартный шрифт и без эмблем. Папку класть до перезапуска.

Наблюдение за прогоном (из корня репозитория, `<run_id>` — имя папки в `runs/`):

```bash
.venv/bin/python scripts/watch.py <run_id> -f               # живая лента: узлы, агенты, ошибки
.venv/bin/python scripts/watch.py <run_id> -f --until-done  # следить до конца разбора
.venv/bin/python scripts/session_report.py <run_id>         # разбор сессии после работы
.venv/bin/python scripts/session_report.py <run_id> --compare <run_id2>  # вердикты «было → стало»
```

**На спарке (прод) — автозапуск и сторож** (с 2026-10-02, после перезагрузки спарка 01.10,
когда сервис и ссылка, запущенные руками в `screen`, не поднялись сами). Три пользовательских
юнита systemd из `deploy/systemd-user/`; у пользователя `masked` включён linger — юниты
стартуют при загрузке без входа в систему, sudo не нужен:

| Юнит | Что делает |
|---|---|
| `p10-web.service` | страница на 8030; при падении — перезапуск через 5 с |
| `p10-tuna.service` | ссылка https://p10-orv.ru.tuna.am (`tuna http 8030 --subdomain=p10-orv --location=ru`); при обрыве — через 10 с |
| `p10-watchdog.timer` → `deploy/p10-watchdog.sh` | раз в минуту: страница отвечает локально, ссылка — снаружи; три провала подряд — перезапуск юнита; события — `var/logs/watchdog.log` |

```bash
cp deploy/systemd-user/p10-* ~/.config/systemd/user/ && systemctl --user daemon-reload
systemctl --user enable --now p10-web p10-tuna p10-watchdog.timer   # установка
systemctl --user status p10-web p10-tuna                             # состояние
systemctl --user restart p10-web                                     # перезапуск (не во время прогона)
journalctl --user -u p10-web -u p10-tuna --since today               # журнал процессов
```

`deploy/p10-orv.service` — прежний системный юнит, ставится через sudo; не используется.

Тесты:

```bash
.venv/bin/pytest -q -m "not live"   # без обращений к модели
.venv/bin/pytest -q -m live         # с реальными вызовами, платно
```

## Настройки

Всё в `app/config.py`:

| Что | Значение | Зачем |
|---|---|---|
| `MODEL` / `EFFORT` | `sonnet` / `medium` | задано явно: иначе CLI возьмёт модель из настроек машины |
| `DIALOG_MODEL` | `= MODEL` | модель помощника в диалоге; отдельной настройкой — выбор модели решает владелец |
| `MAX_CONCURRENT_RUNS` | `2` | одновременных разборов; третий встаёт в очередь |
| `REQUEST_YEARS_DEPTH` | `3` | глубина запроса в годах, текущий год не берётся; снизу окно обрезается годом вступления акта в силу |
| `PASSPORT_TIMEOUT_S` | `1800` | таймаут узла паспорта: на большом акте он идёт до 10 минут, стандартных 900 с не хватает на ретрай после обрыва API |
| `NO_DATA_TEXT_FAMILY` | `{1..6}` | индикаторы, у которых «нет данных» — незавершённая проверка по правовой базе, гипотезы не строятся |
| `ACCEPTED_EXTENSIONS` | `.docx .pdf .doc` | принимаемые форматы |
| `CACHE_WARMUP_S` | `12` | сдвиг старта ведомых агентов группы (2.6): лидер успевает записать акт в кэш, остальные его читают |
| `SEARCH_LIMITS` / `SEARCH_LIMIT_MAX` | `{3: 25, 4: 15, 10: 5, 11: 10}` / `50` | потолки заходов поиска в интернете по индикаторам — по умолчанию для «Настроек прогона» (2.7) |
| `INDICATOR_GARANT_TOOLS` | 3, 4, 10, 11 | какие инструменты Гаранта разрешены каждому индикатору (2.7); остальным — никаких |
| `INDICATOR_TIMEOUT_S` | `{3: 2700}` | индикатор 3 проверяет каждую ссылку акта отдельным вызовом правовой базы — 900 с не хватает |
| `SESSION_IDLE_S` | `3600` | сессия закрывается сама после часа без событий в журнале (2.7) |
| `SERVICE_SYSTEM_PROMPT` | две фразы | системный промпт агентов вместо стандартного промпта Claude Code (2.7) |

## Чего пока нет

- **Второй прогон после ответа органа.** Вердикты «нет данных» должны
  пересчитываться, когда придут запрошенные цифры.
- **Суточный лимит.** Ограничена только одновременность, счётчика за сутки
  нет.
- **В диалоге (2.5):** правка паспорта, автоматический каскад до конца цепочки,
  склейка гипотез моделью, добавление позиции запроса напрямую (и единицы
  площади), работа нескольких людей с журналом по пользователям.
